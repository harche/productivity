# Documentation Structure Reference

This reference defines the file structure, templates, and conventions for knowledge bases generated by Context Keeper.

## File Tree

Every knowledge base follows this layout:

```
project-folder/
  CLAUDE.md              # AI agent entry point — quick context, key links, glossary
  README.md              # Human entry point — overview, decision summary, doc index
  docs/
    problem-statement.md  # The problem/topic, background, options considered
    decision-*.md         # One per major decision — what was chosen and why
    design-*.md           # Implementation details, plans, open questions
    <topic>.md            # Additional topic files as needed
```

Not every project needs all of these. A simple discussion might just need CLAUDE.md + README.md + one doc. Scale up as complexity warrants.

## File Purposes

### CLAUDE.md

The entry point for AI agents. Loaded automatically into every Claude Code session in this directory. Must be concise (under 50 lines) so it doesn't overwhelm the context window.

Contents:
- One-line project description
- Links to source materials (Slack thread URLs, Google Doc URLs, Jira issues)
- Link to README.md as the navigation hub
- Table mapping filenames to what's in them
- Glossary of key technical terms (short definitions only)

Template:

```markdown
# [Project Name] - Project Context

[One-sentence description of what this project is about.]

## Quick Context

- **Origin:** [where this started — Slack link, doc link, etc.]
- **Source Doc:** [link to primary source document if applicable]
- **Decision:** [one-line summary of the key decision, if one was made]

## Documentation Structure

Start with [README.md](README.md) for the full overview.

| File | What's in it |
|---|---|
| [README.md](README.md) | Overview and navigation hub |
| [docs/problem-statement.md](docs/problem-statement.md) | [brief description] |
| [docs/decision-xyz.md](docs/decision-xyz.md) | [brief description] |

## Key Terms

- **Term** — Short definition
```

### README.md

The entry point for humans. Contains the overview, links to source materials, a summary of decisions, and an index of all docs.

Template:

```markdown
# [Project Title]

[2-3 sentence description of the project/topic.]

## Background

[Brief context — what prompted this discussion, where it started.]

**Source document:** [link]
**Slack thread:** [link]

## Decision

[Summary of what was decided. If no decision yet, note that.]

## Documentation

| Document | Description |
|---|---|
| [Problem Statement](docs/problem-statement.md) | [description] |
| [Decision: ...](docs/decision-xyz.md) | [description] |
| [Design Details](docs/design-xyz.md) | [description] |

## Key People

- **Name** (`@handle`) — Role/contribution
```

### docs/problem-statement.md

Summarizes the source material — the problem, background, and options/approaches that were considered. This is a synthesis, not a copy-paste of the original doc. It should stand on its own for someone who can't access the original source.

Structure:
- Link back to source document
- Cross-references to related docs
- Background/context section
- Problem description
- Options/approaches with pros and cons (use tables for comparison)
- Open questions

### docs/decision-*.md

One file per major decision. Captures what was chosen, why, and why alternatives were rejected.

Structure:
- Cross-references to problem statement and design details
- Summary of the decision
- Rationale (the core argument for this choice)
- Why not the alternatives (brief, focused on the deal-breakers)
- Open questions or caveats

### docs/design-*.md

Implementation details, plans, and deep dives. This is where the bulk of detailed content lives.

Structure:
- Cross-references to decision and problem statement docs
- Organized by topic/concern (not chronologically)
- Use tables for structured comparisons
- Use code blocks for technical examples

## Cross-referencing

Every doc in `docs/` should include a header line linking to related docs:

```markdown
**Related docs:** [Problem Statement](problem-statement.md) | [Decision](decision-xyz.md) | [Project README](../README.md)
```

This lets both humans and AI agents navigate between docs without loading everything at once.

## Linking Convention

Every reference to an external resource must be a clickable markdown link. This is non-negotiable — links are how readers find depth and verify claims.

What to link:
- **Jira issues** — `[OCPSTRAT-918](https://issues.redhat.com/browse/OCPSTRAT-918)`
- **Slack threads** — `[#channel-name thread](https://slack-workspace.slack.com/archives/...)`
- **Google Docs** — `[Doc title](https://docs.google.com/document/d/...)`
- **GitHub issues/PRs** — `[repo#123](https://github.com/org/repo/issues/123)`
- **Knowledge base articles** — `[KB article title](https://access.redhat.com/...)`

If you encounter a reference without a URL (e.g., someone mentions "OCPSTRAT-918" in a Slack message), look it up using the available plugins and add the link. If you can't find it, ask the user.

Never write bare references like "see OCPSTRAT-918" or "as discussed in the doc". Always make them clickable.

## Formatting Conventions

- **Tables** for comparing options, listing scenarios, or any structured data
- **Code blocks** for API examples, YAML manifests, CLI commands
- **Bold** for key terms on first use
- Keep paragraphs short — 2-4 sentences
- Use headers liberally — they aid scanning and AI navigation
- No emojis unless the user requests them

## Naming Conventions

- Use kebab-case for filenames: `decision-option-d.md`, not `Decision_Option_D.md`
- Prefix decision docs with `decision-`: `decision-option-d.md`
- Prefix design docs with `design-`: `design-rollout.md`
- Use descriptive names that a reader can understand without opening the file
